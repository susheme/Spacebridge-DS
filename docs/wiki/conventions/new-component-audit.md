# Новый компонент: сначала аудит зависимостей

> Перед новым компонентом в Spacebridge DS — аудит «что есть / чего нет», список дыр юзеру, потом код

Перед тем как писать **новый компонент** в Spacebridge DS — сначала аудит зависимостей, потом работа.

**Why:** агент уже накосячил — собрал чекбокс в табличном хедере как нативный `<input class="sb-checkbox">` вместо DS-компонента `.sb-checkbox > .sb-checkbox-box`. Юзер хочет, чтобы я заранее сверялся с тем, что в DS уже есть, и явно сообщал о недостающем — а не изобретал молча.

**How to apply:**
1. Разложи компонент на части: суб-компоненты, иконки (`ICON_PATHS`/`SB_GLYPHS`), хелперы (`sbMk*`), токены (цвет/размер), sb-* классы.
2. `grep` каждый по `js/`, `css/`, `js/core.js`, `js/tokens.js`, `css/tokens.css`.
3. Используй существующее (см. [reuse-existing-styles](reuse-existing-styles.md)), не самодел.
4. **Напиши юзеру список того, чего не хватает** (нет токена/иконки/суб-компонента/хелпера) и дождись решения. Не придумывай недостающее сам ([figma-tokens-immutable](../infra/figma-tokens-immutable.md)).
5. Только потом — код.

Зафиксировано также в `spacebridge-ds/CLAUDE.md` → раздел «Новый компонент — сначала аудит зависимостей».
